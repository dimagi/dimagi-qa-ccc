# CCCT-2670 LDVP End-to-End Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One hybrid test that takes a worker from a web invite through Learn, a failed and a passed assessment, deliveries, web verification and payment, asserting every case in the CCCT-2670 test plan that a machine can judge.

**Architecture:** A Playwright test (`playwright_web/tests/test_e2e_ldvp.py`) owns the run. It creates a fresh opportunity, invites the worker, then alternates web stages with Maestro device sessions on BrowserStack (`flows.mobile_runner.run_flows`), exactly like `test_e2e_relearn_lifecycle.py`. A session ends wherever web has to act before the device can see the result.

**Tech Stack:** Python 3, pytest, Playwright (sync), Maestro 1.39.13 flows on BrowserStack App Automate, CommCare 2.65 qaAutomation APK.

**Spec:** `test_plans/CCCT-2670_LDVP_Automation_Test_Plan.xlsx` (24 cases; TC-REG-003 is manual, TC-REG-001 needs a long-lived ended opportunity and is out of this plan).

## Global Constraints

- Branch `feature/ccct-2670`, local only. Do not push or open a PR until Kankana's 2.65 work has merged.
- Staging first (`config.env == "stage"`); prod only after staging is green.
- Org `PM_Automation_01` (`flows.olp_setup.PM_ORG`); learn/deliver apps copied from `[Master] Learn App` / `[Master] Delivery App`.
- Payment unit: name `LDVP Visit`, amount `100`, max total `4`, max daily `2`, window 30 days from today.
- Assessment scores: fail `10`, pass `90`; passing score is `40`.
- Visit names `LDVP-V<n>-<stamp>`, ids `<stamp><n>`; stamp = last 6 digits of `int(time.time())`.
- Worker identities come only from `test_data/mobile_workers.yaml` via `WORKER_BY_FLOW`; one worker per environment, never shared with another suite.
- Worker A = `MAESTRO_LDVP_WORKER`, from the same reserved block as `WORKER_INVITES.reserved_invite` (`+74267426090`, which must stay unregistered for Connect_worker_12): staging `+7426 7426091`, prod `+7426 7426093`. Worker B = `MAESTRO_LDVP_UNINVITED`: staging `7426092`, prod `7426094`. The first run's learn/uninvited flows register the number (pre-invited signup, master TC_16); later runs sign in with the backup code. The flow branches on whether the confirm-code / "Welcome back" screen appears.
- Device sessions start with `clearState: true` (a BrowserStack session is a fresh install anyway).

## Review Focus

1. **Staging lag on the HQ -> Connect hop.** A visit or assessment read on web too early looks like a product bug. Every web read after a device session polls (`wait_for_visit`, plus the new `wait_for_worker_status` / `wait_for_assessment`) and never reads once.
2. **Auto-approve on by default.** If the created opportunity auto-approves, V1 and V2 arrive Approved and TC-VER-001/002 prove nothing. Task 2 reads the setting after creation and fails fast with that reason.
3. **Duplicate vs daily limit ordering (plan Q2).** V1, V2, V1-dup, V3: if a duplicate counts toward the daily max, V3 is over limit for the wrong reason. The test asserts each row's own status, so a misattribution fails loudly. It does not pass quietly.
4. **The tapped opportunity is the wrong one.** The worker sees many opportunities, and `shared_open_deliver_app` taps the first `btn_start` on screen. The LDVP flows scroll to the run's exact name and tap inside that card.
5. **A previous run's leftovers.** Unique stamp in the opportunity and visit names; assertions match on the stamp and never on "the latest row".
